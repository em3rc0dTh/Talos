**Status:** PREPARED / BLOCKED BY R1-11

**Program:** R1 — Talos 1.0 Product Completion  
**Prerequisite:** R1-01 through R1-10 closed; R1-11 must report PASS before this gate can certify anything.

## Purpose

R1-12 is the final Talos 1.0 product gate. It does not add product behavior. It certifies one exact merged `main` SHA against the complete release evidence envelope.

The workflow is:

```text
.github/workflows/r1-12-talos-1-release-certification.yml
```

It is intentionally manual (`workflow_dispatch`) because release certification is an authority action, not an automatic side effect of merging code.

## Exact-SHA rule

The operator supplies an `expected_sha`. The workflow checks out that SHA and then independently fetches `origin/main`.

Certification stops unless:

```text
checked-out HEAD == expected_sha == current origin/main
```

A stale commit, feature branch head, detached historical commit, or older passing SHA cannot be relabeled as the current Talos 1.0 release.

## R1-11 hard prerequisite

Before any release tests execute, the workflow runs:

```bash
node --experimental-strip-types ./scripts/r1-11-field-trial-gate.ts ../../evidence/field-trials
```

This requires at least two qualifying receipts from two distinct real process fingerprints. Synthetic tests for the receipt validator never count as field trials.

Evidence contract:

```text
talos.r1-11.field-trial.v1
```

Protocol:

```text
plan/72-R1-11-FIELD-TRIAL-PROTOCOL-v0.1.md
```

## Release envelope

After R1-11 passes, R1-12 verifies the exact SHA with the following envelope:

1. clean `npm ci` from the exact lockfile;
2. architecture verification and B0 frozen baseline verification;
3. B1–B9 semantic/runtime verification;
4. B10 same-build restart verification;
5. complete image/source verification through I7C-06 plus the I8/I9 edge chain;
6. the complete `r1-*.test.ts` product suite;
7. R1-08 with `R1_08_LIVE_REQUIRED=1`, forcing a real GitHub external effect from the complete One-App → Temporal path;
8. fresh-Worker replay proving the external effect is deduplicated rather than repeated;
9. R1-09 restart/runtime-version behavior;
10. secret-safe durable-evidence assertions;
11. exact-SHA release receipt generation.

The permanent real-effect sink is:

```text
GitHub issue #59
Talos 1.0 release certification external-effect sink
```

The issue is evidence storage only. Its existence does not imply release certification.

## Release receipt

Only after every prior workflow step succeeds does this script run:

```text
scripts/r1-12-release-receipt.ts
```

Schema:

```text
talos.r1-12.release-receipt.v1
```

The receipt records:

- exact merged-main SHA;
- workflow run identity;
- qualifying R1-11 trial IDs and distinct-process count;
- real external-effect evidence sink;
- explicit PASS assertions for the release envelope;
- a truth boundary explaining what the receipt does not prove.

The receipt is uploaded as a GitHub Actions artifact instead of being committed back into the certified SHA. This prevents the act of recording the receipt from changing the exact code revision that was certified.

## Product-ready claim

Only a successful R1-12 receipt may authorize:

> **Talos 1.0 — PRODUCT READY**

That claim applies to the exact certified SHA. It does not mean:

- product-market fit is proven;
- multi-customer repeatability is proven;
- scale readiness is proven;
- every external integration is certified;
- future changes inherit certification automatically.

## After a successful R1-12 run

The release operator may then:

1. preserve the workflow run and receipt artifact;
2. tag the certified SHA as the Talos 1.0 release candidate/final release according to repository release policy;
3. publish a release record that references the exact SHA and R1-12 workflow run;
4. make a documentation-only repository update pointing to that already-certified SHA if desired.

Any subsequent product-code change requires a new release certification for the new SHA.
